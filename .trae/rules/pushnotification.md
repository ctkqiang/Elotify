## 1. 代码结构与组织
- 必须遵循标准 Gin 项目布局：
  - `internal/`：私有代码，包按职责分层：`api`（控制器）→ `service`（业务）→ `repository`（数据）。
- 新增包或模块前必须在团队内讨论，获得批准后方可实施。

## 2. 编码规范
- **格式**：必须使用 `go fmt` / `goimports`，并通过 `golangci-lint`（配置见项目根目录）检查。
- **错误处理**：所有错误必须显式处理；业务错误封装为自定义类型，由中间件统一返回。
- **日志**：使用结构化日志（如 `logrus`），包含请求 ID；禁止 `fmt.Println`。
- **Gin 路由**：所有路由集中在 `internal/api/router.go` 注册；中间件顺序固定为：recovery → 日志 → 鉴权 → 限流 → 业务。
- **注释**：关键函数、复杂逻辑必须写中文注释；API 使用 Swagger 文档。

## 3. AWS 集成规范
- **认证**：禁止硬编码密钥；必须通过 IAM 角色（生产）或环境变量（开发）获取凭证。
- **封装**：所有 AWS 服务调用封装在 `internal/repository/aws/`，返回业务层接口。
- **重试与超时**：AWS SDK 必须配置合理的重试策略和超时时间。
- **资源管理**：所有云资源必须通过 Terraform 管理，并打上标签（项目、环境、负责人）。

## 4. 开发流程与“不经同意不得构建”
- **任务关联**：每次提交必须关联 Issue/任务单；分支命名格式：`feature/ISSUE-编号-简述`。
- **代码审查**：
  - 提交 PR 前必须通过本地 `make lint` 和 `make test`。
  - PR 必须至少 2 人批准，且所有讨论已解决。
  - 任何架构变更或引入外部依赖必须提前在团队中提出并获得同意。
- **构建与部署**：
  - 禁止手动构建或部署到生产环境；必须通过 CI/CD 流水线（GitHub Actions / Jenkins）。
  - 遵循开发 → 测试 → 预发 → 生产顺序，生产变更需申请窗口。

## 5. 测试要求
- **单元测试**：每个业务函数必须编写单元测试，覆盖率不低于 80%。
- **集成测试**：关键路径需编写集成测试（放在 `test/integration`，使用构建标签隔离）。
- **性能测试**：核心 API 需满足 SLA，定期进行压力测试。
